# وثيقة عقد التنفيذ المعماري الشامل لعصرنة النظام والأداء وتجربة المستخدم (Master Modernization, Performance & UI/UX Execution Contract)
## الدليل الهندسي الإلزامي لمنظومة Leader for Trans (LFT)

---

**الإصدار:** 3.2 (النسخة النهائية المعتمدة للتنفيذ — Final Approved Execution Contract)  
**التاريخ:** سبتمبر 2026  
**النطاق:** قاعدة البيانات، الـ APIs الميدانية، لوحة التحكم الإدارية بالكامل (Admin Back Office)، منظومة الفواتير والضرائب (ETA)، والعمليات المالية والأسطول.  
**طبيعة الوثيقة:** **عقد تنفيذي ملزم ومغلق (Binding & Finalized Execution Contract)** يحدد بدقة متناهية قواعد العمل، سياج الأمان المالي، محددات التصميم، واشتراطات قبول كل مرحلة دون أي اجتهاد منفرد أو توسع غير معتمد في النطاق (Scope Creep). يتم الانطلاق منه مباشرة لبناء الـ Master Prompt للمرحلة الأولى (Phase 0).

## 1. قواعد وضوابط تنفيذ الوكلاء البرمجيين (Agent Execution Rules)

**يلتزم أي مطور أو مساعد برمجي (Coding Agent) بالقواعد الإلزامية الاثنتي عشرة التالية بصورة صارمة:**

```text
1. العمل حصرياً داخل المرحلة المعتمدة حالياً (Work ONLY on the currently approved Phase).
2. حظر الانتقال التلقائي لأي مرحلة تالية دون تقديم تقرير إغلاق المرحلة الحالية واعتماده.
3. الفحص والتدقيق أولاً قبل كتابة أو تعديل أي كود (Inspect before modifying).
4. حظر افتراض وجود أعمدة بقاعدة البيانات، مسارات (Routes)، صلاحيات، أو علاقات دون قراءتها والتحقق منها برمجياً.
5. حظر حذف كود حالي أو جداول أو بيانات لتسهيل التنفيذ (Never delete existing code/data to simplify implementation).
6. حظر تعديل قواعد العمل والتحقق (Business Rules) لمجرد تمرير الاختبارات (Never change business rules to make tests pass).
7. حظر تغيير عقود الـ API (JSON Keys / Types / Structures) دون موافقة كتابية صريحة.
8. حظر إدخال بيانات تجريبية وهمية (No fake/dummy/demo data) في بيئة التطوير المتصلة بالإنتاج.
9. حظر تنصيب مكتبات أو حزم برمجية جديدة (Major Dependencies / Frameworks) دون مبرر تقني وموافقة مسبقة.
10. التوقف الفوري ورفع تقرير استفسار عند تعارض الوثائق مع الكود الفعلي (Stop and report on conflict).
11. التوقف الفوري ورفع تقرير مالي عند عدم القدرة على إثبات أي قيد مالي (Stop on financial invariant uncertainty).
12. تقديم قائمة بالملفات المعدلة (Changed-files list) وأدلة الاختبارات عند إغلاق كل مرحلة.
```

## 2. المبادئ الهندسية وسياج الأمان (Engineering Invariants & Guardrails)

### 2.1 سياج الأمان المالي الصارم (Financial Integrity Guardrails)
> **القاعدة الحاكمة:** `السرعة والتحسينات البصرية لا يمكن أن تمس الدقة المحاسبية قط`.

أي تعديل يمس العمليات والكيانات المالية (`agent_expenses`, `agent_wallets`, `car_wallets`, `money_transfers`, `custody`, `delivery_policies`, `invoices`, `invoice_payments`, `vault_transactions`, `bank_transactions`) يخضع للاختبارات التالية قبل القبول:
```text
✓ الرصيد قبل العملية = الرصيد بعد العملية (Balance Invariant: Balance Before = Balance After)
✓ منع الخصم المزدوج نهائياً (No Duplicate Debit under any race condition)
✓ منع الإيداع المزدوج نهائياً (No Duplicate Credit under any race condition)
✓ منع فقدان أي حركة مالية (Zero Lost Transactions)
✓ الإلغاء المالي يسترد المبلغ بدقة لمصدره الأصلي (Accurate Void Reversal)
✓ حماية العمليات التزامنية من الصرف المزدوج (Concurrency & Double-Spending Protection via appropriate transactional concurrency controls, e.g. DB locks where required)
✓ استمرار فاعلية مفتاح عدم التكرار (Idempotency via Unique Request Key)
```

### 2.2 مبدأ التوافق المزدوج (Schema & Behavioral Compatibility)
> **القاعدة:** `التوافق الرجعي = توافق هيكل البيانات (Schema) + توافق سلوك التطبيق (Behavior)`.
- بقاء حقول الـ JSON كما هي ليس كافياً؛ إذا كان تطبيق الموبايل الحالي يتوقع استلام كافة مهمات الحاويات ولا يدعم الترقيم، فإن حصر النتيجة في 20 عنصراً يُعد **كسراً سلوكياً خطيراً (Behavioral Breaking Change)** يوقف العمل الميداني.
- **استراتيجية التوافق:**
  1. التحقق من قدرات نسخ تطبيقات الموبايل العاملة حالياً في الميدان قبل تطبيق الترقيم الإجباري.
  2. حظر معامل `all=true` الفضفاض غير المشروط، واستبداله بحد أمان مراقب (Guardrail Cap) مع قياس معدل استدعائه للتخلص منه تدريجياً.

### 2.3 القيود التقنية لإعادة تصميم لوحة التحكم (Phase 4B Technology Constraints)
> **القاعدة:** إعادة تصميم لوحة التحكم هي **تحديث لطبقة العرض والواجهات فقط (Presentation Layer)**.

```text
قواعد بيئة الواجهات (Frontend Stack Constraints):
- تدقيق حزم الـ Frontend المثبتة ومسار البناء (Build Pipeline) القائم قبل بدء التصميم.
- إعادة استخدام الـ Stack الحالي للمشروع (Blade Templates, CSS/SCSS, Vanilla JS / Alpine / jQuery القائم).
- حظر تحويل صفحات Blade إلى React / Vue / Livewire ما لم يُعتمد ذلك بطلب صريح ومستقل.
- حظر استبدال أدوات البناء القائمة (Vite / Mix) دون اعتماد رسمي.
```

### 2.4 حماية عقود النماذج وعناصر الواجهة (Form & DOM Contract Protection)
يُحظر تماماً أثناء إعادة تصميم شاشات الـ Blade حذف أو إعادة تسمية:
```text
- أسماء حقول الإدخال (input names: مثل name="company_id")
- معامِلات الـ Request والـ Query String
- معامِلات مسارات الـ Routes
- الحقول المخفية (hidden inputs: المعرفات والتوكنز)
- مفاتيح التحقق (validation keys والرسائل المرتبطة بها)
- عقود أحداث الجافاسكريبت (Event Listeners & Dispatchers)
- خطافات الـ DOM (data-* attributes و IDs المستخدمة برمجياً)
```

### 2.5 حظر المؤشرات والبيانات الوهمية (No Fake Data / KPIs Rule)
> **القاعدة:** `يُمنع نهائياً اختراع أي بيانات أو بطاقات مؤشرات وهمية`.
- كل رقم أو بطاقة (KPI Card) أو رسم بياني (Chart) في لوحة التحكم يجب أن يرتبط **بمصدر بيانات حقيقي معتمد وموجود بالـ Backend**.
- إذا لم يكن الـ Controller أو الخدمة الحالية توفر الرقم المطلوب: **يُمنع اختراعه أو وضع قيمة تقديرية**؛ يُوثق المؤشر كـ `Unavailable`، ولا يُضاف إلا بعد بناء واعتماد معادلته الحسابية في الـ Backend.

### 2.6 ضوابط الإجراءات الجماعية (Safe Bulk Actions Rule)
- تُحظر الإجراءات الجماعية على تغيير مراحل الحاويات (`Specification → Waiting → Loading → Unloading → Finished`) لأن لكل مرحلة اعتمادات وتكليفات وتوثيق إيصالات مستقل.
- تقتصر الـ Bulk Actions حصرياً على العمليات المدعومة بالفعل بأمان في طبقة منطق الأعمال السابقة (مثل: الطباعة الجماعية، التصدير، أو العمليات المصرح بها).

### 2.7 عزل تصميم الشاشات المالية (Financial UI Boundary)
- خلال **Phase 4B**، تقتصر التعديلات على الشاشات المالية (الفواتير، الخزنة، البنوك، الشيكات، كشوف الحسابات) على **التصميم البصري وتنسيق العرض فقط (Presentation-only)**.
- يُحظر إجراء أي Refactoring للاستعلامات المالية أو الحسابات داخل Phase 4B؛ ويؤجل ذلك بالكامل إلى **Phase 5**.

### 2.8 استراتيجية إخفاق طوابير المهام (Queue Failure Strategy)
- يُحظر التحويل التلقائي الصامت للوظائف الثقيلة (FCM, SMTP, PDF/Excel Generation) إلى `sync` driver في بيئة الإنتاج عند تعطل الـ Workers؛ لأن ذلك يعيد مشاكل الـ Timeouts إلى طلبات الـ HTTP.
- الاستراتيجية المعتمدة: التنبيه الفوري على تعطل الـ Worker، الحفاظ على الوظائف في الطابور، وإعادة تشغيل الـ Workers، وقصر `sync` على الوظائف الحرجة الخفيفة المصرح بها فقط.

## 3. التدقيق البيئي والأساس المرجعي (Phase 0: Environment & Performance Audit)

قبل لمس أي سطر كود، يتم إنجاز **Phase 0** وتوثيق تقرير يشمل:

### 3.4 لقطة السلوك والعقود الحالية (Current Behavior & Contract Snapshot)

## 4. تدقيق وتنفيذ الفهارس وقاعدة الـ Unique Preflight (Phase 1: Index Optimization)

### 4.1 الفحص المسبق للتكرار قبل الـ Unique Index (Preflight Duplicate Audit)
قبل إنشاء فهرس عدم التكرار المالي:
```sql
UNIQUE INDEX uq_agent_expenses_request_key (request_key)
```
**يجب تشغيل الفحص الاستباقي الإلزامي التالي:**
```sql
SELECT request_key, COUNT(*) as cnt
FROM agent_expenses
WHERE request_key IS NOT NULL
GROUP BY request_key
HAVING COUNT(*) > 1;
```
> **شرط حازم:** إذا ظهرت أي سجلات مكررة تاريخياً في قاعدة البيانات، **تتوقف المرحلة فوراً ويُرفع تقرير تدقيق مالي**؛ ويُحظر تماماً على المطور أو الـ AI حذف أو تعديل أي سجل مالي مكرر تلقائياً.

### 4.2 ضوابط الفهارس المركبة
1. **فحص الـ Redundancy:** عدم إنشاء فهرس يكرر بداية فهرس قائم.
2. **ترتيب الأعمدة:** حقول المساواة الصريحة (`Equality =`) أولاً، تليها حقول المجالات والفرز (`Range / Order By`).
3. **تنفيذ الـ Migration:**
   - جدول `booking_containers`: `(booking_id, status, id DESC)`، مسار المراحل، و `container_number`.
   - جدول `bookings`: `(company_id, created_at DESC)`، `(status, created_at DESC)`، و `shipping_agent_id`.
   - جدول `booking_container_agents`: `(agent_id, stage_type, booking_container_id)`.
   - جدول `agent_expenses`: `(booking_container_id, type_id, voided_at)`، و `(agent_id, created_at DESC)`.
   - جدول `delivery_policies`: `(booking_container_id, car_id)`، و `policy_code`.
   - جدول `invoices`: `(company_id, status, created_at DESC)`، و `invoice_number`.

## 5. البنية التحتية للبحث والترقيم (Phase 2: Search Profiles & Query Standards)

### 5.1 معمارية Search Profiles per Resource
- رفض استخدام `Trait` عام يطبق `orWhereHas` المتشعبة العشوائية.
- بناء **Search Scope مستقل ومحدد** لكل Model بقائمة سماح صارمة (Allowlist):
  - **البحث في الأكواد والأرقام:** مطابقة تامة (`=`) أو بادئة (`LIKE 'ABC%'`) للاستفادة الكاملة من B-Tree Index.
  - **قائمة حقول الفرز المسموحة (Sort Whitelisting):** قصر الترتيب على أعمدة مفهرسة ومعتمدة لمنع Filesort.
  - المعاملات القياسية: `search`, `sort_by`, `sort_direction`, `date_from`, `date_to`, `page`, `per_page`.

### 5.2 الترقيم الكلاسيكي وبالمؤشر
- **لوحة التحكم:** استخدام `LengthAwarePagination` لعرض إجمالي الصفحات والتنقل.
- **تطبيقات الموبايل:** تقييم واعتماد `CursorPagination` للشاشات الحجمية عالية التردد (المصروفات والإشعارات).

## 7. لوحة التحكم: الأداء ثم إعادة التصميم (Phase 4A & Phase 4B)

### 7.1 المرحلة 4A: تأسيس أداء الـ Backend للوحة (Admin Performance Foundation)
- دمج استعلامات عدادات المراحل `stageCounts` في `Admin\BookingController` عبر استعلام تجميعي واحد (Conditional Aggregation).

### 7.2 المرحلة 4B: جرد وإعادة تصميم لوحة التحكم بالكامل (Full Admin UI/UX Redesign)

#### أ) الخطوة الإلزامية الأولى: جرد الشاشات (Admin Screen Inventory)
تبدأ المرحلة باستخراج وحصر شاشات لوحة التحكم الفعلية من مسارات `routes/web.php` وملفات الـ Controllers:
```text
مصفوفة جرد الشاشات (Screen Inventory Table):
[الوحدة | المسار | الـ Controller | الـ View | الصلاحية | الحالة الحالية | حالة التجديد | فحص التراجع]
- العمليات والحجوزات (Bookings & Containers)
- العملاء والشركات (Companies & Branches)
- الأسطول والسيارات (Fleet, Cars & Drivers)
- الفريق الميداني (Agents & Super Agents)
- الخدمات والأسعار (Services & Pricing)
- المحاسبة والفواتير (Finance, Invoices & Vault - Presentation Only)
- إدارة المحتوى (CMS)
- الإعدادات والمستخدمين (Settings & Permissions)
```
> **معيار إغلاق المرحلة:** إتمام تجديد 100% من الشاشات المسجلة في جدول الجرد الفعلي دون استثناء.

#### ب) هوية ولغة التصميم الموحدة (Design System)
- لوحة ألوان احترافية مستوحاة من قطاع النقل البحري والبري اللوجستي مع مراعاة تباين الألوان (WCAG AA).
- طباعة عربية متطورة وفائقة الوضوح في الجداول الكثيفة (`Cairo / IBM Plex Sans Arabic`).
- مكونات ذرية كاملة: أزرار، حقول إدخال، شارات حالات المراحل، ونوافذ منبثقة.
- حالات مكتملة للشاشات: **حالة التحميل (Skeleton Loaders)**، **حالة الفراغ (Empty States مع رسائل توجيهية)**، و**حالة الخطأ (Error States)**.

#### ج) تحسينات تجربة المستخدم وسهولة الاستخدام (Ergonomics & Usability)
1. **سهولة الوصول (Accessibility - WCAG AA):** دعم التنقل الكامل بلوحة المفاتيح (Keyboard Navigation)، حالات التركيز (Focus Rings)، وتجنب الاعتماد على اللون وحده لتفسير الحالة.
2. **تفضيلات المستخدم (User Preferences):** إمكانية حفظ حالة طي الشريط الجانبي (Sidebar) وتخصيص الأعمدة الظاهرة في LocalStorage.
3. **حماية العمليات الحساسة (Destructive Actions Guard):** مربعات حوار تأكيدية مخصصة لعمليات الحذف، الإلغاء، أو الرفض مع شرح توضيحي للنتيجة المترتبة، وتجنب الاعتماد على الأيقونات المجردة.
4. **حماية التعديلات غير المحفوظة (Unsaved Changes Warning):** إظهار تنبيه عند محاولة مغادرة النماذج الكبيرة (خاصة نموذج الحجز) قبل الحفظ.

#### د) مسار الحاوية البصري التفاعلي (Visual Container Timeline)
مخطط زمني يعكس المسار الحقيقي المنفذ في الكود:
`Specification (تخصيص) → Waiting (انتظار) → Loading (تحميل) → Unloading (تعتيق) → Finished (مكتمل)` مع إظهار المندوب المكلف، تاريخ الاعتماد، وحالة إقفال إيصالات المصروفات.

#### هـ) شريط التنقل وحماية الصلاحيات (Navigation Authorization & Zero Leaks)
- الشريط الجانبي (Sidebar) الجديد يلتزم حرفياً بنفس مصفوفة الصلاحيات (Spatie Permissions) الحالية دون أي تعديل؛ لا يظهر أي بند أو شاشة لمستخدم لا يملك تصريح الوصول إليها.

#### و) نطاق وضوابط البحث الشامل (Global Search Scope & Guardrails)
- **مقيد بالصلاحيات (Permission-Aware):** يُحظر تماماً على محرك البحث كشف أسماء أو أرقام أو بيانات لأي مورد (Resource) لا يملك المستخدم صلاحية عرضه.
- **خادم ومحدد النطاق (Server-side & Indexed):** يُمنع عمل استعلامات مسح شامل `LIKE %term%` عشوائية عبر كافة الجداول؛ يقتصر البحث على المعرفات المفهرسة الأساسية (`booking_number`, `container_number`, `invoice_number`, `company_name`).
- **محددات الأداء:** حد أدنى لطول نص البحث (3 أحرف على الأقل)، وتحديد سقف أعلى للنتائج المعروضة (Top 5 لكل مورد) لتفادي إنهاك الخادم.

---

## 8. الأمان المالي، الفواتير، والضرائب (Phase 5: Financial Safety & ETA)

- التحقق الشامل من جداول العهد والمحافظ، وحماية الـ Concurrency لمنع الصرف المزدوج.
- عزل عمليات الإرسال والاستعلام الجماعي لمصلحة الضرائب المصرية (ETA) عبر طوابير المهام (Queue Jobs) مع Retry Policy و Timeout حازم و Submission Audit Log.
- تحسين استعلامات الفواتير وتطبيق سطح المكتب (Desktop App).

---

## 9. بوابة العميل وتطبيق الفوترة (Phase 6: Client Portal & Desktop App)

- فرض **Rate Limiting** على مسار التتبع العام المفتوح (Public Tracking) لمنع الاستنزاف والحماية من الـ Scraping.
- تفعيل الـ Pagination على حجوزات وفواتير الشركات المسجلة.
- منع تحميل الملفات والمستندات الثقيلة (Blobs) في قوائم العرض والاكتفاء بالبيانات الوصفية.

---

## 10. طوابير المهام، الكاش، والملفات (Phase 7: Queues, Caching & Media)

- نقل إشعارات FCM، رسائل البريد الإلكتروني SMTP، وتوليد ملفات الـ PDF/Excel الكبيرة إلى طوابير العمل في الخلفية.
- اعتماد سياسة الكاش الحذرة: حظر كاش الأرصدة المالية، وقصر الكاش على البيانات المرجعية شبه الثابتة مع Model Observers للتنظيف الفوري.
- ضبط معالجة المرفقات وتوليد نسخ مصغرة (Thumbnails) لتسريع العرض الميداني والإداري.

---

## 11. الأمان والتدقيق المستمر وسجل العمليات (Security & Audit Trail)

### 11.1 تدقيق الأمان والصلاحيات (Security Regression)
> **القاعدة:** إخفاء العنصر أو الزر في الـ UI هو مجرد إجراء تنظيمي؛ كل إجراء يجب أن يخضع للتحقق الصارم في الـ Backend.
- التحقق من حماية كافة مسارات العمليات ضد ثغرات CSRF، XSS، Mass Assignment، و IDOR.
- فحص قيود رفع الملفات وحماية مسارات التحميل الميداني.

### 11.2 سجل التدقيق للعمليات الحساسة (Audit Trail)
الحفاظ على تسجيل: `(who, what, when, entity, old value, new value, request source)` للعمليات الحساسة:
- إلغاء أو تعديل الفواتير.
- تسجيل المدفوعات والشيكات.
- إلغاء المصروفات الميدانية (`void expense`).
- تحويلات العهد والمحافظ.
- اعتمادات مراحل التشغيل.
- تسوية بوليصات التسليم.

---

## 12. استراتيجية الاختبارات المستمرة (Continuous Testing Strategy)

**يُمنع تأجيل الاختبارات إلى نهاية المشروع؛ كل مرحلة تتضمن حزمة اختبارات تحقق خاصة بها:**

```text
متطلبات فحص وإغلاق كل مرحلة (Per-Phase Verification):
1. Phase Tests: كتابة وتشغيل اختبارات آلية مخصصة للوظائف المعدلة.
2. Regression Suite: تشغيل حزمة الاختبارات القائمة للتأكد من عدم كسر أي وظيفة.
3. Financial Invariant Tests: فحص تطابق الأرصدة ومنع التكرار (في المراحل المالية).
4. Static Analysis & Code Style: فحص الكود والتأكد من خلوه من الأخطاء الصامتة.
5. Query Evidence: تشغيل EXPLAIN للتأكد من استخدام الفهارس وغياب N+1.
6. Git Diff Audit: مراجعة التغييرات سطراً بسطر والتأكد من عدم المساس بأي كود غير معني.
```

### المرحلة 8: اختبارات النظام الشاملة والأحمال (Phase 8: Full Regression & Load Testing)
- **Contract Tests:** مطابقة دقيقة لاستجابات الـ API السابقة والحالية.
- **Financial Regression Tests:** محاكاة ما لا يقل عن 1,000 عملية مالية تمثيلية (حيثما تسمح البيئة) مع التركيز الصارم على جودة السيناريوهات: محاكاة التزامن المكثف (Concurrency)، محاولات الصرف المزدوج (Double-spending)، مفاتيح عدم التكرار (Idempotency)، وعمليات الإلغاء (Void Reversals) للتأكد من ثبات الأرصدة.
- **Concurrency & Load Tests:** محاكاة طلبات متزامنة مكثفة للتحقق من عدم حدوث Race Conditions أو Deadlocks.
- **Visual Regression Audit:** التحقق من اكتمال وجودة واجهات شاشات الـ Blade مقارنة بجرد الشاشات.

---

## 13. النشر، خطة التراجع، والمراقبة (Phase 9: Rollout, Monitoring & Rollback)

- أخذ نسخة احتياطية كاملة (Full Database & Storage Backup) قبل البدء.
- **تصنيف استراتيجية التراجع لكل Migration (Classified Migration Rollback):**
  1. **التراجع العكسي الآمن (Safe Reversible Migration):** استخدام دالة `down()` للتغييرات الهيكلية الآمنة (مثل إسقاط الفهارس المستحدثة التي لا تؤدي لفقد أي بيانات).
  2. **إجراءات الإصلاح للأمام أو الاستعادة (Forward-Fix / Point-in-time Restore):** للـ Migrations التي تتضمن قيوداً مالية أو تحويراً للبيانات حيث يُعد التراجع عبر `down()` خطراً قد يسبب فقدان بيانات تاريخية أو تلفاً في الاتساق المالي.
- تشغيل الـ Migrations في نافذة صيانة محسوبة واختبار مسار التطبيق.
- تفعيل مراقبة سجل الاستعلامات البطيئة (Slow Query Log > 500ms) ومراقبة عمق الـ Queues ومعدل أخطاء 5xx.
- وجود خطة تشغيلية واضحة ومجربة للتراجع السريع (Rollback Runbook).

---

## 14. بروتوكول إغلاق المراحل واعتمادها (Phase Closure Protocol)

**قاعدة إلزامية لا استثناء فيها:**
> **يُمنع منعاً باتاً إغلاق أي مرحلة واعتبارها منتهية لمجرد أن "الكود يعمل بدون أخطاء ظاهرة".**  
> يجب تقديم تقرير إغلاق رسمي للمرحلة يحتوي على:
> 1. قائمة الملفات التي تم تعديلها أو إنشاؤها.
> 2. نتائج مقارنة الأداء (Performance Evidence) مقارنة بـ Phase 0.
> 3. نتائج اختبارات الـ Regression والتحقق المالي والعقود البرمجية.
> 4. استيفاء شروط جرد الشاشات والفحص البصري للمراحل المتعلقة بواجهات المستخدم.
