# التحميل والتعتيق المتوازيان

## قواعد التشغيل المنفذة

- وحدة العمل هي الحاوية `booking_containers`، وليست الحجز بالكامل.
- يظل `status` والتواريخ وأعلام الاعتماد الموجودة مصدر حالة التشغيل، لتفادي وجود نسختين متعارضتين من الحالة.
- `booking_container_agents.stage_type` هو هوية مرحلة التكليف الثابتة: `0` تخصيص، `1` تحميل، `2` تعتيق. لا يتغير بانتقال حالة الحاوية.
- جدول `booking_container_stages` يحفظ إقفال إيصالات كل مرحلة ومن أقفلها وتوقيت الإقفال ورقم إصدار محتوياتها. عدم وجود سجل يعني أن الإيصالات مفتوحة، والإصدار الأول هو `1`.
- إنهاء التحميل يسمح بطلب اعتماد المسؤول؛ اعتماد التحميل هو شرط تعيين/بدء التعتيق. اعتماد التشغيل لا يقفل الإيصالات.
- تعيين مندوب للتعتيق يستبدل تكليفات التعتيق فقط؛ تكليفات التحميل محفوظة. يمكن تعيين نفس المندوب للمرحلتين، وأكثر من مندوب للمرحلة نفسها.
- يستمر التسليم الحالي من التخصيص إلى التحميل لنفس المندوبين إذا لم يوجد تكليف تحميل. التعتيق يحتاج تكليفًا صريحًا.
- يظل التحميل والتعتيق ظاهرين للمندوب المكلّف حتى إقفال إيصالات المرحلة، حتى بعد أكثر من 24 ساعة. سجل التخصيص يحتفظ بفلترة العرض القديمة.
- بعد اكتمال تشغيل المرحلة، إضافة المصروفات وإيصالاتها متاحة ما دامت مفتوحة. حقول التشغيل وصور أوراق التشغيل عبر مسارات التحميل/التعتيق لا تقبل تعديل المندوب بعد الاكتمال.
- الإيصال الذي عليه `admin_approval` لا يعدله أو يلغيه المندوب. المسؤول يستطيع التصحيح ما دامت إيصالات المرحلة مفتوحة.
- اعتماد/إقفال الإيصالات بواسطة المشرف إجراء مستقل متاح بمجرد إتاحة المرحلة، قبل اعتماد التشغيل أو بعده، وبعد مراجعة النسخة الحالية من الإيصالات. لا ينقل الحاوية إلى المرحلة التالية، واعتماد التشغيل لا يقفل الإيصالات تلقائيًا. لا توجد إعادة فتح تلقائية أو مهلة إقفال تلقائية.
- الرجوع إلى مرحلة سابقة مرفوض إذا وُجد تكليف أو مصروف للمرحلة التالية أو إقفال إيصالات للمرحلة المعنية؛ لا تُحذف أعمال المرحلة التالية لإتمام الرجوع.

## عقد التطبيق

هذا المستودع يحتوي على الباك إند وواجهات الإدارة، ولا يحتوي على مشروع تطبيق الموبايل. يلزم تنسيق تحديث الموبايل مع النشر؛ تغييرات حماية المصروفات ليست متوافقة بالكامل مع النسخ القديمة.

### تعيين المندوبين

`POST /api/superagent/booking/assign_agents`

```json
{
  "booking_container_ids": [100],
  "type_id": 2,
  "agent_ids": [25]
}
```

استخدم `booking_container_ids` لمعرّفات الحاويات الفعلية، أو `booking_ids` لمعرّفات الحجوزات. المعامل القديم المفرد `booking_container_id` كان مستخدمًا لمعرّفات الحجوزات داخل هذا المسار؛ احتُفظ بهذا المعنى للتوافق. لا ترسل الشكلين معًا؛ الحاويات الصريحة لها الأولوية.

`agent_ids: []` يزيل تكليفات المرحلة المحددة فقط. في حالة حذف `type_id` يختار السيرفر مرحلة التشغيل حسب الاعتمادات؛ يفضل إرساله صراحةً من الشاشة، خصوصًا عند تعديل تكليف مرحلة سابقة. جميع تعيينات الطلب الواحد ذرية.

### عرض مهام المندوب

مسارات التحميل والتعتيق الحالية باقية وبنفس شكل التجميع. كل حاوية داخل التجميع تُعرض بسياق القائمة التي جاءت منها. المفاتيح المهمة:

```json
{
  "id": 100,
  "type_id": 1,
  "stage_type": "loading",
  "operational_stage": "unloading",
  "stage_status": "approved",
  "is_completed": true,
  "is_approved": true,
  "can_upload_receipts": true,
  "can_complete_stage": false,
  "receipts_closed": false,
  "receipts_version": 3
}
```

احتفظ بمفتاح الشاشة `(container_id, type_id)`. لا تستبدل سياق شاشة التحميل بقيمة `operational_stage`، ولا تدمج بطاقتين لنفس الحاوية في مرحلتين مختلفتين. اتبع `can_upload_receipts` و`can_complete_stage` لإظهار الأزرار؛ يتحقق السيرفر من الصلاحيات أيضًا.

### إنشاء إيصال مصروف

المساران الحاليان `make_general_expenses` و`make_reservation_expenses` يحتاجان `request_key` جديدًا لكل إيصال. يجب حفظه محليًا قبل الإرسال وإعادة استخدامه عند إعادة محاولة نفس الإرسال، بما في ذلك بعد انقطاع الاتصال أو إعادة تشغيل التطبيق.

```json
{
  "booking_container_id": 100,
  "booking_id": 50,
  "type_id": 1,
  "service_id": 4,
  "value": 150,
  "notes": "إيصال تحميل متأخر",
  "request_key": "mobile-generated-uuid"
}
```

`booking_id` مطلوب لمسار الحجز؛ يتحقق السيرفر من مطابقته للحاوية. `type_id` مطلوب عند تحديد الحاوية، ولا يُستنتج من حالتها الحالية. للمصروف العام غير المرتبط بحاوية يجوز عدم إرسال الحاوية والمرحلة.

إعادة نفس المفتاح بنفس البيانات تعيد الإيصال الموجود دون خصم إضافي. إعادة المفتاح ببيانات مختلفة تعطي `409`. حد المفتاح 80 حرفًا. الاستجابة أصبحت تحتوي `data` به الإيصال، إضافةً إلى مفاتيح النجاح المعتادة، ومنها `version` و`type_id` و`booking_container_id` و`request_key` و`voided_at`.

### تعديل وإلغاء الإيصال

`POST /api/agent/update_expense`:

```json
{"id": 900, "version": 1, "value": 175, "notes": "تصحيح القيمة"}
```

`POST /api/agent/delete_expense`:

```json
{"id": 900, "version": 2}
```

احفظ `version` من آخر قراءة. إصدار قديم يسبب `409` ويحتاج تحديث البيانات ومراجعة التعديل؛ لا تعاود الإرسال تلقائيًا برقم إصدار جديد. لا يسمح بتغيير الحاوية أو مرحلة إيصال موجود.

الإلغاء منطقي عبر `voided_at`: تُرد القيمة مرة واحدة، ويخرج الإيصال من استعلامات Eloquent والتقارير العادية، وتبقى بياناته ومفتاح إرساله للمراجعة ومنع الإرسال المتأخر من إعادة إنشائه. إعادة إرسال إنشاء إيصال ملغى تعيد السجل الملغى؛ على التطبيق مراعاة `voided_at`. احتُفظ بصور الإيصالات القديمة عند التصحيح/الإلغاء.

مصروفات العهد تستخدم مصدر أموالها عند التصحيح/الإلغاء، وتُرفض بعد تسوية العهدة. إنشاء مصروف السيارة/العهدة عبر `make_car_expenses` يبقى مسارًا مستقلًا لا ينشئ إيصال مرحلة؛ الحماية الجديدة للإنشاء تخص مساري المصروفات العامة ومصروفات الحجز المذكورين أعلاه.

### مراجعة وإقفال المسؤول

1. `GET /api/superagent/booking/pending_stage_receipts?type_id=1` يعرض الحاويات المكلّف بها مندوبون والمتاحة للتحميل التي ما زالت إيصالات تحميلها مفتوحة، قبل اعتماد التشغيل أو بعده، في صفحات من 50 عنصرًا. استخدم `2` للتعتيق بعد اعتماد التحميل.
2. `GET /api/superagent/booking/stage_receipts?booking_container_id=100&type_id=1` يعيد قائمة المصروفات وإصدارها المتسق `receipts_version` وحالة الإقفال.
3. بعد مراجعة هذه القائمة، أرسل:

```http
POST /api/superagent/booking/close_stage_receipts
```

```json
{"booking_container_id": 100, "type_id": 1, "receipts_version": 3}
```

إذا أضيف أو عُدّل أو ألغي إيصال بعد قراءة القائمة، يرفض الإقفال بـ`409`. حدّث القائمة ليُراجعها المسؤول مجددًا. بعد الإقفال، يختفي تكليف المرحلة من قائمة المندوب المفتوحة ويستمر ظهور المصروفات في السجلات والتقارير.

### أخطاء يجب أن يعالجها التطبيق

- `401`: الجلسة غير صالحة؛ مسارات إنهاء التشغيل وأوراق الحاوية تتطلب الآن تسجيل دخول المندوب أيضًا.
- `403`: المندوب غير مكلف بالمرحلة أو لا يملك الإيصال.
- `409`: المرحلة مقفولة، إصدار قديم، إعادة استخدام مفتاح إرسال ببيانات مختلفة، أو محاولة انتقال غير مسموحة.
- `422`: حقول ناقصة أو غير صحيحة أو رصيد غير كافٍ.

رفع أوراق السيارة يتطلب `type_id` بقيمة `1` أو `2` لتحديد سياق العملية. إضافة إيصال تحميل متأخر تتم عبر مسار المصروفات، وليس مسار تغيير بيانات التحميل.

## البيانات القديمة والنشر

الترحيل `2026_09_13_000001_add_parallel_container_stages.php` يضيف الجداول/الأعمدة ولا يعيد كتابة إيصالات أو أرصدة قديمة. يسند للتكليف القديم المرحلة التي تمثلها أعلام اعتماده الموجودة. هذا استنتاج للحالة الحالية، وليس استعادة مؤكدة لتاريخ تكليفاته.

الكود القديم كان يحذف التكليفات عند إعادة التعيين ويحدّث أعلام جميع التكليفات معًا؛ لذلك لا يمكن استعادة مندوب التحميل التاريخي بشكل موثوق من السجلات الحالية وحدها. قبل النشر راجع التكليفات القديمة، وأعد تعيين التحميل صراحةً للحاويات التي تحتاج إيصالات متأخرة. لا تُمنح صلاحية تحميل تاريخية تلقائيًا لمندوب التعتيق. القوائم المكتملة قد تظهر بعد الترحيل حتى إقفال إيصالاتها؛ ينبغي مراجعتها عند الانتقال.

ترتيب النشر:

1. تجهيز نسخة موبايل تتعامل مع الحقول والطلبات السابقة، وتجربة التكامل على نسخة اختبار من البيانات.
2. أخذ نسخة احتياطية ومراجعة تعيينات المراحل الحالية وأي نسخ تطبيق قديمة لا تزال مستخدمة.
3. إيقاف الكتابة لفترة النشر، وتطبيق الترحيل قبل تفعيل الكود الجديد. النموذج يستخدم الأعمدة الجديدة، فلا يُشغّل مع المخطط القديم.
4. تحديث الباك إند والتطبيق، ومراجعة مثال بمندوبين ومثال بنفس المندوب.

```shell
php artisan migrate --path=database/migrations/2026_09_13_000001_add_parallel_container_stages.php
```

لا تُرجع الترحيل بعد بدء استعمال المراحل أو المصروفات الجديدة دون تسوية البيانات؛ عملية `down` ترفض حذف بيانات الإقفال ومفاتيح الإرسال المستخدمة. الرجوع إلى نسخة باك إند قديمة بعد إنشاء تكليفات متوازية غير آمن أيضًا.

## التحقق

```shell
php vendor/bin/phpunit tests/Feature/ParallelContainerStagesTest.php
```

الاختبارات تستخدم SQLite في الذاكرة ومخططًا معزولًا، وتختبر الخدمة ومسارات HTTP والقوائم والصلاحيات والإصدارات وإلغاء الإيصال والترحيل. لا تلمس قاعدة المشروع.

القفل في الإنتاج يعتمد على معاملات MySQL/InnoDB وقفل الحاوية أولًا ثم السجلات ذات الصلة. قراءة حالة إقفال المرحلة تكون قراءة مقفولة كي لا تستعمل لقطة قديمة تحت `REPEATABLE READ`. اختبارات SQLite لا تثبت انتظار الأقفال بين اتصالين MySQL فعليين؛ يجب إجراء اختبار اتصالين متزامنين في بيئة التجربة قبل النشر.

في البيئة الحالية، بيانات الاتصال بقاعدة المشروع رُفضت أثناء `migrate:status`، لذلك لم يُطبّق الترحيل عليها. الاختبار الافتراضي `Feature/ExampleTest` يتوقع `200` للمسار `/` بينما المسار الحالي يحوّل إلى `main` باستجابة `302`؛ هذا منفصل عن اختبارات المراحل الجديدة.
